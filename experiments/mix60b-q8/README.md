# mix60b-q8: Qwen3-8B, three training signals in the mix60b order

Three Qwen3-8B runs with the stage order and environment of `experiments/mix60b`: long context first (60 steps from the
NVFP4 start, YaRN x4, window 131,072, WSD decay over the last 15), then reasoning, code, function calling and customer
service (240 steps from the long-context stage's step 60, native RoPE, window 40,960, decay over the last 40). The three
runs differ only in the training signal:

| Arm | Training signal | Lists (stage 1 / stage 2) |
|---|---|---|
| `sft` | **SFT traces.** A row whose source dataset has a written reply for exactly its prompt is trained on that reply as written (no generation); a row without one is generated by the student. Forward KL to the teacher on the response tokens. | `mix60sft_s2_long_q8_s20261026` / `mix60sft_s1_q8_s20261026` |
| `mkl` | **Mixed KL.** The student's own rollouts (on-policy), loss 0.5 KL(teacher ‖ student) + 0.5 KL(student ‖ teacher). | `mix60_s2_long_q8_s20261023` / `mix60_s1_q8_s20261023` |
| `rkl` | **Reverse KL.** The student's own rollouts, loss KL(student ‖ teacher) only. | `mix60_s2_long_q8_s20261023` / `mix60_s1_q8_s20261023` |

The same two stages with forward KL on the student's own rollouts are the reference run; it is not part of this
experiment.

| Config | Stage | Steps (decay) | Start | Exported |
|---|---|---|---|---|
| `<arm>_stage1.toml` | long context | 60 (last 15) | the NVFP4 start | `mix60b-q8-<arm>-s060` (not evaluated) |
| `<arm>_stage2.toml` | mixed | 240 (last 40) | the arm's stage-1 step 60 (new optimizer and schedule) | `mix60b-q8-<arm>-s300` |
| `smoke_<arm>_long.toml`, `smoke_<arm>.toml` | 2-step checks of both paths | | | |

Shared settings: `stage1.toml`, `stage2.toml`, `../mix60/base.toml`, and for stage 2 the multi-turn environment
`../mix60b/base_mt.toml` (mix60's with code_v3, log_v3 and close_v4, see `experiments/mix60b/README.md`). Learning rate
1e-5 → 1e-6, 36 packs of 131,072 tokens per step, 5-step warmup. Do not change them (CLAUDE.md, rule 6). The loss weight
is the config key `kd_reverse` (0 = forward KL, the default), passed to the trainer as `CL_KD_REVERSE`. The only free
knobs are the layout (`--layout`) and the output directory (`--out`).

## The SFT-trace lists

`mix60sft_*` are the mix60 Qwen3-8B lists with a `response` column (`SUBSET.json` describes them):

- **Which rows have a trace.** A trace counts only if it was written for exactly the row's prompt and fits the window
  (prompt + response). It is kept as written: replies without reasoning (Qwen3's empty think block), calls of functions
  the tool list lacks, Chinese replies. For math the trace of the row's effort level without python, else another
  level's; otherwise one picked at random (seed 20261023). Rows without a usable trace have no response and are
  generated by the student in the same run, like the other arms' rows: about 4 % of each list.
- **SFT-SWE-v2** rows keep the list's prompt, which drops the formatting paragraph of the dataset's own prompt (as in the
  other arms). The dataset's replies were written for the prompt with that paragraph: a reply that uses that formatting
  is not used (the row is generated), the others are trained as written under the list's prompt.
- **Multi-turn conversations** of the customer-service portion with a trace are one sample each: the recorded final
  answer is the response and every earlier assistant answer in the prompt is supervised too (`hist_sup`). Every
  customer-service conversation has one; the multi-turn rows without one are function-calling conversations, played as
  in mix60 (user turns replayed, tool results simulated).
- **Sizes.** Written traces are mostly shorter than the student's answers, so each domain is continued along its own row
  sequence until it holds the same packed tokens as the mix60 list (60 steps of data per domain), counting a generated
  row as mix60 estimates it, then a 10 % buffer (code and function calling hold more than that already: cut along the
  mix60 order, the rows after the cut as the buffer, 10 % and 9 %). The lists therefore have more rows than the mix60
  ones: stage 2 94,510 training rows (mix60: 70,543), stage 1 11,954 (10,325).

## Requirements

As `experiments/mix60/README.md`, "Requirements", for one model per node; Qwen3-8B needs no optimizer offload. The
simulator API variables are needed for every stage-2 config and `smoke_<arm>.toml` (all three arms: the `sft` lists keep
generated function-calling conversations, whose tool results the simulator writes), not for stage 1.

## Running

One arm per node (or one after another on the same node, each with its own `--out` or the same one: the chains have their
own names). Pull first (`git status` clean).

```bash
setup/setup.sh data                      # the four Qwen3-8B lists of release data-v4 (about 2 GB)
python3 tools/check_env.py --deep        # all ok (host warnings only)
(cd train && ../.venv-client/bin/python tests/test_chain_mix60b_q8.py && ../.venv-client/bin/python tests/test_multiturn_v4.py)
export QADX_API_BASE=... QADX_API_KEY=... QADX_SIM_MODEL=...   # the training simulator (gpt-oss-120b), for stage 2
E=experiments/mix60b-q8; A=sft                                  # this node's arm: sft, mkl or rkl
python3 train/launch/chain.py $E/${A}_stage1.toml prepare        # the start checkpoint and PTQ student ("exists" after round 4 / pairs-r2)
python3 train/launch/chain.py $E/${A}_stage1.toml check-step0    # only if it never passed for Qwen3-8B
python3 train/launch/chain.py $E/smoke_${A}_long.toml run --layout 1node   # stage-1 path, 2 steps; smoke checks
python3 train/launch/chain.py $E/smoke_${A}.toml run --layout 1node        # stage-2 path (from the smoke's step 2), 2 steps; smoke checks
python3 train/launch/chain.py $E/smoke_${A}.toml clean && python3 train/launch/chain.py $E/smoke_${A}_long.toml clean   # after both passed
python3 train/launch/chain.py $E/${A}_stage1.toml run --layout 1node   # 60 steps of long context: exports mix60b-q8-$A-s060
python3 train/launch/chain.py $E/${A}_stage2.toml run --layout 1node   # 240 mixed steps from stage 1's step 60: mix60b-q8-$A-s300
```

The step-0 check: go on only with `VERDICT PASS` in `out/check-step0.txt` (criteria: `experiments/mix60/README.md`,
"Order of work").

**Smoke checks.** The five checks of `experiments/mix60/README.md` ("Smoke runs, what to check"), with
`N=smoke-mix60b-q8-<arm>-long`, `S=smoke-mix60b-q8-<arm>-long-s002` for the first smoke and `N=smoke-mix60b-q8-<arm>`,
`S=smoke-mix60b-q8-<arm>-s002` for the second, and these differences:
- Check 2, memory: Qwen3-8B prints no `offload optimizer step 2` lines.
- Check 3, weight push: `smoke_<arm>_long` starts from the checkpoint on disk, so the push count is **8**; for `mkl` and
  `rkl` in both steps `nll_s` below 1.0 and `top1` above 0.8 (YaRN servers). `smoke_<arm>` starts from the first smoke's
  weights, pushed before step 0: the count is **12**. The step 2 / step 1 comparison as in mix60. For `sft` the `nll_s`
  and `top1` bounds and the step comparison do not apply (most response tokens are written traces, not the servers'
  samples): report the values; the push counts apply. For `mkl` and `rkl` the trainer log
  starts with `qad_distill: KD loss = 0.50 forward KL + 0.50 reverse KL` (`mkl`) or `0.00 forward KL + 1.00 reverse KL`
  (`rkl`); report the line. `kl` in `metrics.jsonl` is then the mixed or reverse value.
- Check 4, multi-turn episodes: the stage-2 smoke only. For `sft` only the function-calling conversations without a
  trace are played, so there are few episodes, possibly none in 2 steps. For `sft` also report the written-trace and
  generated response tokens of each smoke step:
  ```bash
  python3 -c "import json,sys; [print(r['step'], r.get('offline_tokens'), r.get('gen_tokens')) for r in map(json.loads, open(sys.argv[1])) if r.get('route') == 'pack']" out/runs/$S/steps.jsonl
  ```
  Pass: `offline_tokens` above 0 and above `gen_tokens` in every step of both smokes.
- Check 5, time per step: report it per arm (`mkl` computes both KL directions).

Send the output of the five checks for both smoke runs, also when all pass. The reminders and `CHAIN_STOP` handling of
mix60's README apply (with these names).

**Disk.** `clean` a chain once its exports exist. Run `clean` of `<arm>_stage1.toml` only after stage 2 has started,
that is once `out/mix60b-q8-<arm>.chain.log` shows `INIT_CKPT_OK iter_0000060` (stage 2 lays out its start into
`out/train/mix60b-q8-<arm>-s240.init`). Smoke exports are not needed after the smokes' `clean`: then
`rm -rf out/exports/smoke-mix60b-q8-*`.

## Evaluation

After an arm's stage 2, on the same node, as mix60's evaluation (`experiments/mix60/README.md`, "Evaluation"; tau2 with
gpt-5.2 as the customer and judge). Only the final exports are evaluated:

```bash
.venv-client/bin/python eval/run.py --arm mix60b-q8-sft-s300 --dry-run
nohup .venv-client/bin/python eval/run.py --arm mix60b-q8-sft-s300 > eval-mix60b-q8-sft.log 2>&1 &   # likewise -mkl- and -rkl-
```

mix60b-q8-<arm>-s300 --report`, every row as printed); whether both chains finished (`CHAIN_DONE` in
